# 0009 步骤模板与自动分配 id

- 状态：accepted
- 日期：2026-08-31

## 背景

配置页有两个实际使用中暴露的问题。

其一，任务与目标的 `id` 是可编辑输入框。目标 `id` 改动后 `selection.targetId` 仍指向旧值，
`task.targets.find(...)` 返回 `undefined`，整个 `TargetEditor` 被卸载重建，
表现为「输入一个字符就失焦」。任务 `id` 那侧虽同步了 selection，但 `<TriggerEditor key={task.id}>`
每次按键都会强制重挂载。`id` 本身只是内部引用，用户没有编辑它的需求。

其二，一个任务下挂多个目标目录时，各目标的步骤往往完全相同
（OSG 分支 1 / 分支 2 / pub1 / ty1 都是 `revert-generated` + `svn-update`）。
步骤只能逐目标各存一份，调整一次要改 N 遍，改漏就产生静默的行为差异。
缺的是「步骤序列」这一层可复用抽象。

## 决策

**id 由程序自动分配，界面只读。** 新建走 `autoId(prefix, taken)` 给出 `task-1` / `target-1` / `tpl-1`，
复制目标时 `id` 另行分配，不再从显示名派生。显示名和路径仍保留结尾序号递增的便利逻辑。
用户要区分目标就改显示名，`id` 退回纯内部标识。

**新增顶层 `stepTemplates`，目标通过 `usesTemplate` 引用。** 模板持有 `steps` 与变量声明 `vars`，
目标用 `vars` 填各自的取值。差异用 `${变量名}` 占位表达，另有无需声明的内置量
`${target.path}` / `${target.name}` / `${target.id}`。取值优先级为
内置 < 模板默认值 < 目标显式取值。

**模板在配置解析阶段展开。** `parseConfigDetailed` 于路径解析后、语义校验前调用 `expandStepTemplates`，
把引用替换为实际步骤。调度器、CLI、仪表盘等下游完全不感知模板的存在，
既有的参数校验与 toolset 解析逻辑一行未改。

## 权衡

模板可以做成引用式（保持引用，运行时展开）或展开式（保存时摊平）。
选引用式：展开式一保存就丢失复用关系，等于没解决问题。代价是 `configToDraft`
必须保留 `usesTemplate` 而非回填展开后的步骤，否则编辑器保存一次就把模板摊平。

变量语法沿用 `${...}`，不引入表达式求值或条件分支。模板意在消除重复，不是做一套 DSL；
真需要分支就让该目标解除引用，改用自有步骤。

删除模板不阻断：仍在引用它的目标会就地回填展开后的步骤，配置不会变成非法状态。
`extractTemplateFromTarget` 抽取模板时会把步骤里出现的目标路径字面量换成 `${target.path}`，
避免模板写死某一个目录。

## 影响

- `EditorTarget` 新增可选 `usesTemplate` / `vars`；`steps` 在引用模板时为空数组。
- `targetSchema.steps` 由 `.min(1)` 放宽为 `.default([])`，改由展开阶段确保非空。
- 配置页左栏新增「步骤模板」区，目标目录内新增「步骤来源」下拉、「抽成模板」与「解除引用」。
- v1 迁移产物补 `stepTemplates: []`。既有 v2 配置无此字段时按空数组处理，向后兼容。
